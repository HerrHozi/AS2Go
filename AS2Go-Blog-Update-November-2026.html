AS2Go — From Attack Simulation to Repeatable Defender Workshops

Offline preview, SafeMode, and a clearer demo experience: how AS2Go has evolved since May, and what that means for your next defender workshop.

The next step after the introduction

In May, I introduced the updated AS2Go PowerShell module and its approach to demonstrating Active Directory attack paths. Since then, I have continued working on how those demonstrations are prepared, explained, and run.

The original AS2Go 2026 post covered the module structure, the kill-chain approach, and scenarios such as Kerberoasting, AD CS ESC1, and domain persistence. Those remain part of the story.

This follow-up focuses on the experience around those techniques: exploring the workflow before execution, limiting selected actions with SafeMode, and making demonstrations easier to follow.

A useful workshop gives defenders something to investigate, explain, and improve.

Explore the workflow before running it

One of the additions since May is an offline preview. It lets you browse workflow descriptions and source steps without executing the workflow itself.

# Browse the workflow without running its actions
Start-AS2GoDemo -Preview

# Explore a specific phase
Invoke-ASPhase07PrivilegeEscalation -Preview

The preview uses a separate navigation path. It inspects the available functions and displays descriptions or source expressions rather than running the attack steps. The preview path does not perform workflow setup, Active Directory queries, or external tool execution.

This is useful when preparing a session: review the sequence, decide which steps need explanation, and identify the prerequisites to check in the lab. Preview does not demonstrate that an attack would succeed or that a detection would fire.

SafeMode: more control during a demonstration

SafeMode is another addition in the current development build. The main demo passes -SafeMode to the phases it invokes. Selected steps then restrict their execution choices, allowing the presenter to explain an action and skip it.

For example, the current interactive confirmation in Phase 12 offers only Skip when SafeMode is enabled. Phases 10 and 11 also skip their main data-access or copy action in SafeMode, including their unattended branches. Selected Pass-the-Ticket and PsExec prompts have additional restrictions.

Preview and SafeMode serve different purposes

Preview browses the workflow without executing its actions. SafeMode participates in the normal workflow and applies restrictions where implemented. Setup, queries, logging, and other operations can still occur.

ModeWhat to expectBest use
PreviewOffline navigation through descriptions and source steps.Preparation and explanation before execution.
SafeModeNormal workflow with selected execution choices restricted or skipped.Guided demonstrations in a prepared, authorized lab.
Lab executionSelected actions can run and generate observable activity.Testing behavior, telemetry, and detections.

SafeMode is not a universal dry-run or a production safety boundary. Its coverage depends on the phase and execution path. In the reviewed build, Phase 12's unattended branch bypasses the interactive Skip restriction. Do not combine SafeMode with -UnAttended and assume that every action is blocked.

For a walkthrough that must not execute workflow actions, use Preview. For execution, use an isolated lab with test accounts, test data, and a reset plan.

Make the demonstration easier to follow

The October changes include revisions to the demo entry point, function help, console output, and the Pass-the-Ticket workflow. Ticket inspection helpers were also added to support working with Kerberos ticket information.

The current development work continues that direction with consistent phase pages and more specific explanations of what each phase demonstrates. During a workshop, those explanations help connect a technical action with the security lesson behind it.

The data-access phase is a good example. Its sample password file demonstrates why plaintext password storage matters. The backup-copy phase uses simulated backup data to demonstrate exposure through accessible shares. These are teaching scenarios; a sample .dit file is not evidence that a real Active Directory database was extracted.

Explain operational impact one action at a time

Domain compromise and persistence were already covered in May. Since then, Phase 12 and its supporting functions have been reorganized and revised, including backdoor-account creation, account disruption, Group Policy Template manipulation, encryption, and reboot actions.

The revised menu also includes a way to select or change the configured break-glass account. Specific account-disruption and group-manipulation routines contain exclusions for designated accounts. Those exclusions should be understood in the context of each action; they do not guarantee that a lab remains recoverable.

For a defender workshop, focus on one question at a time. Who can change a privileged group? What activity is visible when a policy template changes? Which response would contain the incident, and which recovery steps would still be required?

Turn a demonstration into a defender exercise

A practical session can follow this sequence:

  1. Choose one learning objective. Define the behavior you want to explain or the detection you want to investigate.
  2. Review the workflow. Use Preview to inspect the relevant phase and discuss prerequisites.
  3. Prepare the isolated lab. Verify the selected mode and action, test identities, telemetry collection, and reset procedure.
  4. Run the selected activity. Record the time, source, target, account, and observed outcome.
  5. Compare expectations with evidence. Review events, alerts, and response actions in the connected security tools.
  6. Reset and repeat. Change one condition and investigate how the result differs.

This is a suggested workshop method, not an automated AS2Go reporting feature. An action completing does not prove that monitoring detected it. An action failing does not, by itself, prove that a security control blocked it.

Try it in your lab

AS2Go continues to bring together Active Directory findings, attacker behavior, and defensive visibility. The recent changes make it easier to prepare the explanation around an attack path and choose which parts to explore or execute.

Start with the preview. Review SafeMode's coverage for the build you are using. Then select a focused lab exercise and examine the evidence it produces.

AS2Go remains intended for isolated, explicitly authorized lab and test environments. It is not intended for production use.

Feedback is especially useful when it includes the module version, lab prerequisites, expected behavior, and what you actually observed.
